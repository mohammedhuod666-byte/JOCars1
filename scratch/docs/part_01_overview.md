# الفصل الأول: نظرة عامة على المنصة والبنية التقنية

## ما هي منصة JO Cars

JO Cars منصة أردنية لبيع وشراء السيارات، وصفها وصف المشروع `jo-cars-marketplace` بأنها منصة سيارات «Premium Cars Trading Platform» تجمع بين السوق المفتوح وبين أدوات الذكاء الاصطناعي لتقييم الأسعار ووصف المركبات.

الهدف الأساسي أن تكون الوجهة الواحدة التي يبدأ منها المشتري البحث عن سيارته، ويُنهي فيها البائع صفقة، ويدفع فيها التاجر أعماله، وتحصل فيها الورشة على عملاء.

الفئات المستهدفة:

- **مشترو السيارات:** يتصفّحون الإعلانات، ويقارنون، ويشاهدون تقرير الحالة والسعر العادل، ويراسلون البائع.
- **البائعون الأفراد:** ينشئون إعلاناتهم بأنفسهم ويتلقّون الرسائل داخل المنصة واتصالات عبر واتساب.
- **التاجر والمعرض:** يدير معرضه بملف تجاري عام وتقارير مبيعات ومشاهدات.
- **أصحاب الورش:** يفتحون صفحة ورشة، ويستقبلون مواعيد ومراجعات وينشئون عروض أسعار.
- **الزوار غير المسجّلين:** يتصفّحون ويبحثون ويستخدمون الحاسبات والأخبار دون حساب.

نطاق المحتوى داخل المنصة:

- **سيارات مستعملة:** بحث ومقارنة وإضافة إعلان (`/cars`, `/cars/add`, `/cars/compare`).
- **قطع غيار:** قسم مستقل للبيع والشراء (`/parts`).
- **لوحات سيارات:** عرض وإضافة لوحات للبيع (`/plates`).
- **مزادات:** مزادات سيارات مع مزايدات وسجل مزايداتي (`/auction`, `/my-auctions`, `/my-bids`).
- **ورش صيانة:** صفحات الورش ولوحة تحكم الورشة (`/workshops`, `/workshops/dashboard`).
- **محتوى إخباري ومجتمعي:** أخبار السيارات (`/news`)، والمنتدى للمواضيع والردود (`/forum`).
- **خدمات مساندة:** طلبات الشراء المطلوبة (`/wanted`)، العروض (`/deals`)، الجملة (`/wholesale`)، السيارات المصدمة (`/salvage`)، حاسبات الجمارك والتمويل وتكلفة التملك والصيانة.

## الأطراف الأربعة في المنصة

يوجد نوع واحد للحسابات في قاعدة البيانات، وتُحدَّد رتبته بالحقل `role` المعرَّف في `src/types/index.ts` بالقيم `USER | DEALER | TRADER | ADMIN`، وقيمته الافتراضية عند التسجيل هي `USER` كما هو مكتوب في `prisma/schema.prisma`.

| الطرف | القيمة في الكود | ماذا يستطيع |
|---|---|---|
| الزائر / المستخدم | بدون تسجيل، أو `USER` | الزائر يتصفّح ويبحث؛ والمستخدم يضيف إعلانات وقطع غيار ولوحات، ويحفظ المفضلة، ويراسل البائع، ويشارك في المنتدى، ويدير كراجه ونفقات صيانته |
| التاجر / المعرض | `TRADER` (تاجر) و`DEALER` (تاجر مميّز) | ملف تجاري عام بالاسم والشعار والعنوان ورقم السجل التجاري، صفحة عامة في دليل المعارض، لوحة تاجر وتقارير، وشارة تاجر معتمد بعد موافقة الإدارة |
| صاحب الورشة | مستخدم عادي يملك سجلاً في موديل `Workshop` | ينشئ ورشته من `/workshops/create`، ثم يدير من `/workshops/dashboard` المواعيد والأسعار والخدمات والمراجعات والإعلانات |
| المدير | `ADMIN` | لوحة `/admin` كاملة: المستخدمون، اعتماد التجار، مراجعة الورش، التقييمات، تذاكر الدعم، الإعدادات، وحذف أو تعديل أي محتوى |

قدرات الدور تُفحص في الخادم إمّا عبر `requireRole('ADMIN')` من `src/lib/auth.ts`، أو عبر مقارنة مباشرة مع `user.role === 'ADMIN'` داخل معالج المسار.

> **ملاحظة:** التاجر يُسجَّل بـ `role='TRADER'` مع `dealerVerified=false`، فتحصل على ملفه التجاري فوراً لكن بحالة «غير معتمد». يرفع الإدارة الاعتماد من `/admin/users` أو `/admin/traders-approval`، وبعدها تُفتح له ميزات المعرض الكاملة مثل صفحة المواعيد.

> **ملاحظة:** المدير مستثنى من الحظر التلقائي الذي يفرضه نظام `sentinel` المراقب للإساءات، ولا يمكن أن يُوقَف حسابه آلياً.

## البنية التقنية

المنصة مبنية على Next.js بالوضع القصري (App Router) بلغة TypeScript، مع خادم Node مخصص يشغّل التطبيق ويستضيف قنوات اللحظي.

| المكوّن | التقنية | الدور في المشروع |
|---|---|---|
| إطار العمل | `next` (App Router) | الصفحات ومسارات الـ API، وملف `server.js` يشغّل التطبيق مع `socket.io` ويقدّم ملفات `/uploads` بروابط تخزين مؤقت |
| الواجهة | React 18 + Tailwind CSS 3.4 | التصميم وحركات `framer-motion` وأيقونات `lucide-react` |
| اللغة | TypeScript 5.4 | أنواع مشتركة في `src/types/index.ts` وتحقق ثابت عبر `npm run typecheck` |
| قاعدة البيانات | Prisma ORM 5.14 + **PostgreSQL** | `datasource db` يستخدم `provider = "postgresql"` ويتصل بـ `env("DATABASE_URL")` |
| الحالة في المتصفح | Zustand 5 | مخازن المقارنة والفلاتر والواجهة والإشعارات في `src/store/index.ts`، ومخزن مصادقة `useAuth` يحفظ الجلسة بوساطة `persist` |
| المصادقة | JWT (`jsonwebtoken` + `jose`) مع `bcryptjs` | كوكي `token` من نوع HttpOnly و`SameSite=Strict` مدته 7 أيام، مع تدوير الرمز ورموز OTP |
| رفع الصور | Cloudinary أو تخزين محلي | إن وُجدت متغيرات Cloudinary الثلاثة تُرفع الصورة إليها، وإلا تُحفظ في `public/uploads` بعد ضغطها إلى WebP داخل `/api/upload` |
| البث اللحظي | Ably + Socket.IO | قنوات Ably باسم `conversation:{id}` للرسائل، و`socket.io` داخل `server.js` |
| الذكاء الاصطناعي | NVIDIA NIM | عميل موحّد في `src/ai/nvidia-client.ts` يستهدف `https://integrate.api.nvidia.com/v1` |
| واتساب | UltraMsg | إرسال رسائل عبر `ULTRA_MSG_TOKEN` مع توحيد رقم الهاتف الأردني إلى صيغة `962` |
| التحقق والحماية | Zod + `src/lib/rate-limit.ts` | تحقق من المدخلات، و12 سياسة حد للطلبات (مثل الدخول 5 محاولات كل 15 دقيقة) |
| النشر | Railway + Docker | `railway.json` يبني بـ Nixpacks ويشغّل `node server.js` مع فحص صحة على `/api/health` |

عدد النماذج المتاحة للذكاء الاصطناعي أربعة مع تسلسل بديل تلقائي عند التعطل: `openai/gpt-oss-20b` (الافتراضي)، `z-ai/glm-5.3`، `moonshotai/kimi-k3`، و`mistralai/mistral-large-2-instruct`.

أوامر العمل الأساسية في `package.json`:

```bash
npm run dev        # تشغيل الخادم المخصص server.js
npm run build      # بناء النسخة الإنتاجية
npm run typecheck  # فحص الأنواع
npm run test:e2e   # اختبارات Playwright
npm run db:push    # مزامنة مخطط Prisma مع قاعدة البيانات
```

> **ملاحظة:** حاوية النشر في `Dockerfile` تبني على `node:20-bullseye-slim`، بينما يحدّد `package.json` إصدار Node ‏`24.x` للتشغيل. متغير `DATABASE_URL` يُمرَّر وقت التشغيل فقط ولا يُحفر داخل الصورة.

## دورة حياة الطلب (Request Lifecycle)

عند فتح أي صفحة محمية تتسلسل الأحداث كالتالي:

1. يطلب المتصفح الصفحة من الخادم، فتُعيد الصفحة مع كود JavaScript الخاص بها.
2. يستدعي المكوّن الخطاف `useAuth` من `src/hooks/useAuth`، الذي يقرأ المستخدم من مخزن Zustand المحفوظ ويجدّده من `/api/auth/profile`.
3. ينفّذ المكوّن `fetch` إلى مسار داخل `src/app/api` مع رأس `Authorization: Bearer …` أو كوكي `token`.
4. يستقبل معالج المسار الطلب ويدعو `authenticateRequest(request)`، الذي يتحقق من الرمز ويجلب المستخدم من Prisma ويرفض المحظور أو غير النشط.
5. ينفّذ المعالج الاستعلام عبر Prisma ثم يعيد الرد بـ `successResponse` أو `errorResponse`.
6. يفحص المكوّن `success` ويحدّث الحالة، فتظهر البيانات أو رسالة الخطأ.

مثال مختصر لمسار محمي:

```ts
// src/app/api/garage/route.ts
export async function GET(request: NextRequest) {
  const user = await authenticateRequest(request).catch(() => null);
  if (!user) return Response.json({ success: false, error: 'غير مصرح' }, { status: 401 });

  const garage = await prisma.userGarage.findMany({
    where: { userId: user.id, isActive: true },
    include: { expenses: { orderBy: { date: 'desc' }, take: 5 } },
    orderBy: { createdAt: 'desc' },
  });

  return Response.json({ success: true, data: { cars: garage } });
}
```

> **ملاحظة:** `authenticateRequest` تُعيد `null` بدل رمي خطأ، لذلك يعيد المعالج استجابة `401` بنفس الشكل في كل المسارات.

## قواعد الاستجابة الموحّدة

تعود جميع الردود الناجحة والمكسورة بإطار JSON واحد، وتضيف الدوال في `src/lib/api.ts` ترويسة `Content-Type: application/json; charset=utf-8` حتى تُعرض الحروف العربية سليمة في كل العملاء.

```json
{ "success": true, "data": { "cars": [] } }
{ "success": false, "error": "غير مصرح لك بالوصول" }
{ "success": false, "error": "خطأ في التحقق من البيانات", "details": [] }
```

الدوال المتاحة: `successResponse(data, status)`، `errorResponse(message, status)`، `unauthorizedResponse()`، `notFoundResponse(resource)`، `validationErrorResponse(zodError)`.

حالات HTTP الشائعة:

| الحالة | المعنى | متى تظهر |
|---|---|---|
| 401 | غير مصادق | لا يوجد رمز JWT أو انتهت صلاحيته |
| 403 | ممنوع | الدور غير كافٍ، أو الحساب موقوف، أو `canPost=false` |
| 404 | غير موجود | السجل غير موجود أو لا يخص المستخدم |
| 409 | تعارض | محاولة مكررة، مثل تقييم بائع سبق تقييمه |
| 422 | بيانات غير صالحة | فشل تحقق Zod مع قائمة الحقول الخاطئة |
| 429 | تجاوز الحد | تفعّل سياسة حد للطلبات أو رموز OTP |
| 503 | الخدمة غير متاحة | فشل تخزين الصورة أو تعذّر خدمة الذكاء الاصطناعي |

> **ملاحظة:** بعض المسارات القديمة تعيد `{ "error": "…" }` فقط؛ عند قراءة ردّ جديد راجع أولاً هل استخدم دوال `src/lib/api.ts` أم كتبت الرد يدوياً.

## نطاق الدليل وما يستثناه

يغطي هذا الدليل كل ما يخصّ المستخدم النهائي وصاحب الحساب: التسجيل وتسجيل الدخول، البحث والإعلانات، المزادات واللوحات وقطع الغيار، لوحة التاجر ولوحة الورشة، ولوحة المدير.

كما يشرح من ناحية تقنية قصيرة: شكل الاستجابات، دورة الطلب، وخريطة المجلدات، لتسهيل قراءة الأعطال.

أما ما يستثناه فلا يشمله:

- إعداد بيئة التطوير والنشر التفصيلي وأوامر سطر الطرفية بوصفها دليلاً للمطوّر.
- تصميم قاعدة البيانات والـ schema التفصيلي والـ migrations.
- أكواد المصدر كاملاً أو إعادة كتابة أي كود داخل المشروع.
- السياسات التجارية والاشتراكات والأسعار، ما لم ترد أرقامها صراحة في الواجهة.
