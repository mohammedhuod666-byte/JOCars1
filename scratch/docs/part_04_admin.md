# الفصل الرابع: لوحة تحكم المدير بالكامل

لوحة التحكم هي الواجهة الخلفية لسوق JO Cars: تدير منها المستخدمين والتجار والإعلانات والورش والمحتوى والإعدادات.
يغطي هذا الفصل شجرة `/admin` كاملة، وهي في النسخة الحالية **36 صفحة** (ملف `page.tsx` لكل صفحة)، بينها صفحة رئيسية و32 بطاقة توجيه وثلاث صفحات للمقالات.
كل رقم ونص عربي في هذا الفصل مأخوذ من الكود الفعلي في `src/app/admin/` و`src/app/api/admin/`، لا من التخمين.

## الدخول إلى اللوحة وآلية الحماية

### أين تظهر روابط الدخول

تظهر ثلاثة روابط تؤدي إلى `/admin` داخل الواجهة العامة، ولا يظهر أي منها لغير المدير:
قائمة الترويسة في `src/components/layout/Header.tsx`، وقائمة المستخدم الجانبية في `src/components/layout/UserMenuSheet.tsx`، وشريط التنقل السفلي في `src/components/layout/MobileBottomNav.tsx`.
يمكنك أيضاً كتابة `/admin` في شريط العنوان مباشرة، فالحماية لا تعتمد على إخفاء الرابط.

### طبقة الحماية الأولى: الواجهة العميلة

المشروع **لا يحتوي على `src/middleware.ts`**، أي لا توجد بوابة تحقق تُنفَّذ قبل تحميل الصفحة على مستوى الحافة.
كذلك **لا يوجد `layout.tsx` مشترك** داخل `src/app/admin/`، لذلك كل صفحة إدارة تتكرر بنفس فحص الدور في مكوّنها الخاص:

```ts
useEffect(() => {
  if (_hydrated && (!isAuthenticated || user?.role !== 'ADMIN')) {
    router.push('/');
    return;
  }
}, [_hydrated, isAuthenticated, user, router]);
```

وفي الموضع نفسه تُخفي الصفحة نفسها عن غير المدير بعبارة `return null` حتى لا تُعرض لحظة واحدة.
التوكن يُقرأ من متجر الحالة عبر `useAuth.getState().token` ويُرسل في ترويسة `Authorization: Bearer`.

### طبقة الحماية الثانية: الخادم

كل مسار تحت `src/app/api/admin/` يستدعي `authenticateRequest(request)` من `src/lib/auth.ts` للتحقق من JWT،
ثم يفرض الدور إما بـ `user.role !== 'ADMIN'` أو بـ `requireRole('ADMIN')(user)`، وأي طلب بلا ترويسة صالحة يرد بـ `401`.

```ts
import { authenticateRequest } from '@/lib/auth';
import { unauthorizedResponse } from '@/lib/api';

export async function GET(request: NextRequest) {
  const user = await authenticateRequest(request);
  if (!user || user.role !== 'ADMIN') return unauthorizedResponse();
  // من هنا فصاعداً: استعلام قاعدة البيانات وإرجاع النتيجة
}
```

الجلسة نفسها تُدار في `src/lib/auth.ts`: إصدار التوكن عند تسجيل الدخول، والتحقق منه في كل طلب، والعمل بآلية تدوير (rotation) للتوكن.

> الترتيب المهم: الحماية الحقيقية هي فحص الخادم. صفحات الواجهة العميلة هي مجرد اختصار لمنع عرض الصفحة، فإذا فُتح API مباشرة بتوكن صحيح سيُنفَّذ دائماً، وإذا ضُيع فحص الواجهة بقيت البيانات محمية برد `401`.

> ثغرة مرصودة: صفحة `src/app/admin/workshops/page.tsx` هي الوحيدة بلا فحص `user?.role !== 'ADMIN'` في الواجهة العميلة. البيانات تبقى محمية لأن `src/app/api/admin/workshops/route.ts` يرفض غير المدير، لكن الصفحة تُعرض لغير المدير بحالة فارغة بدل إعادة توجيهه.

## نموذج الأدوار والصلاحيات

يوجد أربعة أدوار فقط في قاعدة البيانات، وتظهر أسماؤها العربية نفسها في فلاتر ونوافذ إدارة المستخدمين.

| الدور | الاسم في الواجهة | من يحصل عليه | النتيجة العملية |
|---|---|---|---|
| USER | مستخدم | كل من يسجّل حساباً | التصفح والمشاركة حسب صلاحيات النشر |
| TRADER | تاجر | تلقائياً عند اعتماد طلب تاجر | `dealerVerified = true` ونسخ ملف التاجر على الحساب |
| DEALER | تاجر مميّز | يُمنح يدوياً من نافذة تعديل المستخدم | يُحسب مع TRADER ضمن بطاقة «التجار» |
| ADMIN | مدير | يُمنح يدوياً من نافذة تعديل المستخدم | يفتح كل مسارات `/api/admin` |

### من يمنح دور «تاجر»

تُدار الطلبات من صفحة `/admin/traders-approval` على نموذج `TraderVerification` بحالات `PENDING` و`APPROVED` و`REJECTED`.
الضغط على «اعتماد» ينفّذ معاملة واحدة (`prisma.$transaction`) تكتب الدور `TRADER` و`dealerVerified = true` واسم المتجر وشعاره ووصفه وعنوانه وإحداثياته وسجله التجاري، ثم تحوّل حالة الطلب إلى `APPROVED`.
ذلك يمنع حالة الواجهة أن يقول «مقبول» بينما الحساب لم يُوثَّق بعد، أو العكس.
الرفض يسجّل سبباً على صف الطلب ليظهر للمتقدم، ويُختم بكل من تصرّف بالتدقيق مع عنوان IP.

```http
POST /api/admin/traders-approval
Authorization: Bearer <admin-token>
Content-Type: application/json

{ "requestId": "clx...", "action": "APPROVE" }
```

### حدود تعديل المستخدمين

نافذة التعديل في `/admin/users` تعرض الأربعة أدوار للاختيار، لكن التوثيق مختلف: التعليق في الكود ينص على أن `dealerVerified` لا يُمنح من هذه النافذة إطلاقاً، بل حصراً عبر صفحة اعتماد التجار.
الحذف الجماعي عبر `/api/admin/users/bulk` يتجاهل حسابات المدير تلقائياً (تظهر في رد `skipped`)، والإجراءات الجماعية للحظر تتطلب سبباً وإلا ظهرت رسالة «سبب الحظر مطلوب للإجراء الجماعي».
الحذف الذاتي مرفوض من `/api/admin/users/[id]` ما لم يصل طلب بـ `force=true`.

### التدقيق والحاسبة

كل إجراء حساس يُسجَّل عبر `createAuditLog` من `src/lib/audit.ts`، وأمثلة الأفعال المسجَّلة: `TRADER_APPROVE` و`TRADER_REJECT` و`BULK_USER_UPDATE` و`UPDATE_SITE_SETTINGS` و`BACKUP_CREATED` و`SENTINEL_BAN` و`SENTINEL_PROBE_BAN` و`TICKET_CLOSE` و`LOGIN`.
تقرأ هذه الأفعال لاحقاً من صفحة «سجل النشاطات» في القسم الخاص بها أدناه.

## الصفحة الرئيسية لللوحة

افتح `/admin` فتظهر عنوان «لوحة التحكم» فوق ثلاث مناطق: مؤشرات سريعة، إشعارات، وأدوات.
تُجلب المؤشرات من `GET /api/admin/stats` بتوكن المدير، والبطاقات الثمانية مرتَّبة كما في الكود:

| البطاقة | الحقل في الرد | مصدر القيمة |
|---|---|---|
| كل السيارات | `totalCars` | عدّ الإعلانات غير المحذوفة |
| نشطة | `activeCars` | الحالة `APPROVED` |
| قيد المراجعة | `pendingCars` | الحالة `PENDING` |
| مباعة | `soldCars` | الحالة `SOLD` |
| المستخدمين | `totalUsers` | عدّ كل الحسابات |
| التجار | `totalDealers` | العقود `DEALER` و`TRADER` |
| المشاهات | `totalViews` | مجموع أعمدة `views` |
| الإيرادات | `revenue` | ثابت `0` في الكود حالياً |

تحت المؤشرات تأتي منطقة الإشعارات: العنوان «الإشعارات» وزر «تحديد الكل مقروء»، والبيانات تأتي من `GET /api/admin/notifications` ويُعلَّم كُلها مقروءاً عبر نداء `POST` على المسار نفسه.
ثم بطاقة «استيراد أخبار السيارات» وزر «استيراد الآن»، الذي ينفّذ `POST /api/admin/news-aggregator` لجلب أخبار السوق مرة واحدة يدوياً.
هذا المسار نفسه مجدول يومياً الساعة 06:00 بتوقيت الخادم في `vercel.json` ضمن قائمة `crons`.
أخيراً شبكة «إدارة سريعة»، وهي اختصارات منظَّمة إلى الصفحات الأكثر استخداماً مثل المستخدمين والسيارات والباقات.

## دليل الصفحات الإدارية

هذا القسم يمرّ على الصفحات الثماني الأساسية بتفصيل كامل، ثم على بقية الصفحات في مجموعات موجزة.

### إدارة المستخدمين `/admin/users`

هذه هي مركز الثقل: بحث فوري بالاسم أو البريد أو الهاتف (مع اختصار «/» للتركيز)، وفلاتر الأدوار (كل الأدوار، مستخدم، تاجر مميّز، تاجر، مدير) وفلاتر الحالات (كل الحالات، محظور، موقوف، النشر متوقف) وترتيب (الأحدث، الأقدم، آخر دخول، آخر ظهور، الأكثر سيارات).
حالة كل حساب تظهر كشارة: «مفعّل» أو «محظور مؤقت» أو «محظور دائم» أو «موقوف» أو «النشر متوقف»، مع مؤشر «متصل الآن» لمن ظهر خلال أقل من خمس دقائق.
الأعمدة تشمل الدور والشارات والحالة والسيارات وتاريخ الانضمام، والنقر على الصف يفتح لوحة جانبية تفصيلية فيها إحصاءات الحساب وقائمة إجراءاته.

تدعم الصفحة ثلاث عمليات جماعية على تحديد متعدد: تفعيل/تعطيل النشر، الحظر المؤقت والحظر الدائم (مع سبب إلزامي)، وإلغاء الحظر، وكلها تمرّ بـ `POST /api/admin/users/bulk` وترد بـ `updated` و`skipped`.
زر «تصدير CSV» يصدّر حتى 2000 سطراً بعناوين `id, name, email, phone, role, isActive, canPost, banStatus, lastLoginAt, lastSeenAt, cars, createdAt`، ويعرض «تم تصدير N مستخدم».
الإجراءات الفردية: تعديل بيانات الحساب مع اختيار الدور الأربعة عبر `PUT /api/admin/users/[id]`، وتعطيل الحساب، وإيقاف النشر، والحذف النهائي عبر `DELETE` على المسار نفسه، وإدارة الشارات عبر نافذة «إدارة شارات المستخدم» المرتبطة بصفحة `/admin/badges`.

```http
PUT /api/admin/users/<id>
Authorization: Bearer <admin-token>
Content-Type: application/json

{ "name": "أحمد", "role": "TRADER" }
```

> ملاحظة: التوثيق `dealerVerified` غير موجود في نموذج التعديل هذا عمداً؛ اعتماد التاجر يتم من صفحة `/admin/traders-approval` فقط.

### إدارة السيارات `/admin/cars`

الصفحة تفتح افتراضياً على تبويب «قيد المراجعة»، مع تبويبات «مقبول» و«مرفوض» وعدّاد حي لكل تبويب يجلبه `GET /api/admin/cars?counts=true`.
البحث يقبل رقم الإعلان (Ref Code) أو اسم البائع أو البريد، كما ينص نص الحقل حرفياً: «بحث برقم الإعلان (Ref Code) أو اسم البائع أو البريد...».
الجدول ثماني أعمدة: الصورة، السيارة، الرمز، البائع، السعر بالدينار الأردني، مميزة، الحالة، الإجراءات.

لكل صف مجموعة أزرار: معاينة الإعلان في صفحة عامة، تمييزه أو إلغاء تمييزه، إدارة وسومه، منح أو إلغاء «شارة الفحص المعتمد»، والحذف النهائي.
نافذة التمييز بعنوان «تمييز الإعلان» تعرض الباقات النشطة من `GET /api/admin/plans` مع المدة والسعر، ويؤكد الزر «تأكيد التمييز» عبر `POST /api/admin/cars/[id]/feature`، وإلغاء التمييز عبر `DELETE` على المسار نفسه.
نافذة «إدارة الوسوم» تجلب الوسوم النشطة من `/api/admin/tags` وتضيف أو تزيل الوسم فوراً عبر `POST` و`DELETE` على `/api/car-tags`.

أزرار القبول والرفض تظهر فقط للإعلانات `PENDING`، وكل تغيير حالة يمرّ بـ `PUT /api/admin/cars/[id]` ثم يُحدّث العدّادات.
نص تأكيد الحذف: «هل أنت متأكد من حذف هذا الإعلان؟ لا يمكن التراجع عن هذا الإجراء.»، ونص تأكيد شارة الفحص: «منح شارة الفحص المعتمد لهذا الإعلان؟».
عند فشل العملية تظهر رسائل مثل «فشل التحديث» أو «فشل الحذف» مع سبب السيرفر إن وجد.

### محرك التقييم `/admin/valuations`

العنوان «محرك التقييم (Valuation Engine)» ووصفه «مراقبة كاملة بدل الصندوق الأسود — كل رقم قابل للتتبع»، وله سبعة تبويبات تغطي دورة حياة التقييم.
الطلب يُوجَّه كـ `GET /api/admin/valuations?view=<tab>&page=1&limit=20` بتوكن المدير، وتبويب «إعادة التقييم» له مسار خاص `GET /api/admin/valuations/revalue`.

| التبويب | ما يعرضه | أعمدة الجدول |
|---|---|---|
| عمليات التقييم | كل طلبات التقييم ونتائجها | الطلب، المستخدم، الحالة، التقدير، الثقة، العينة، التاريخ |
| البيانات المستوردة | عينات السوق المجمّعة | المصدر، السيارة، السنة، كم، السعر، الحالة، الجمع |
| إعادة التقييم | أسطول الإعلانات المعتمدة | قائمة بطاقات بآخر تقييم لكل سيارة |
| الأخطاء | الطلبات الفاشلة | نفس أعمدة عمليات التقييم |
| المشكوك فيها | تقييمات ثقتها منخفضة | الطلب، التقدير، الثقة، العينة، التاريخ |
| أداء النموذج | مؤشرات الجودة | بطاقات: كل الطلبات، مكتملة، متوسط الثقة، متوسط العينة |
| الإعدادات | عتبات المحرك | نموذج إعدادات واحد |

تبويب «البيانات المستوردة» يدعم الإضافة اليدوية بزر «+ إضافة مقارنة يدوية موثقة» وحقول الماركة والموديل والسنة والممشى والسعر والمدينة ورابط الإعلان، والحفظ عبر `POST /api/admin/valuations/listings`.
تبويب «الإعدادات» يضبط ثلاث قيم: «أدنى عينة (رفض تام تحتها — افتراضي 2)» و«الحصة اليومية/مستخدم» و«عمر الإعلان الشاذ (يوم)»، مع أوزان تشابه بصيغة JSON، والإرسال عبر `POST /api/admin/valuations`.
القيم الافتراضية المخزَّنة: `minIncluded = 2` و`dailyQuota = 5` و`staleDays = 60`، وأي نص غير صالح يرد بخطأ «أوزان التشابه ليست JSON صالحاً».

زر «إعادة تقييم هذه الصفحة» يقسّم السيارات إلى دفعات من 5 ويرسلها تباعاً إلى `POST /api/admin/valuations/revalue` مع عزل فشل كل سيارة، ويقيّم التقدّم بسطور مثل «الدفعة 1: 5/5 نجح».
تبويب «أداء النموذج» يرسم آخر 14 يوماً بعدد الطلبات ومتوسط الثقة لكل يوم.
روابط الطلبات داخل الجداول تشير إلى `/api/valuations/<id>` لعرض تفاصيل الطلب كـ JSON.

```http
GET /api/admin/valuations?view=requests&page=1&limit=20
Authorization: Bearer <admin-token>
```

### اعتماد التجار `/admin/traders-approval`

العنوان «اعتماد التجار»، وفلاتره أربعة: «معلق» و«مقبول» و«مرفوض» و«الكل»، والتحميل عبر `GET /api/admin/traders-approval?status=PENDING`.
كل بطاقة طلب تعرض بيانات المتقدم وملف المتجر المطلوب (الاسم والوصف والعنوان والسجل التجاري)، وشارته: «معلق» أو «مقبول» أو «مرفوض».

الإجراء الأساسي زر «اعتماد»، فتنفذ واجهة `POST /api/admin/traders-approval` بـ `{ requestId, action: "APPROVE" }` وتعرض نجاحاً باسم المتجر: «تم اعتماد التاجر «اسم المتجر»».
الإجراء الثاني «رفض»، ويفتح نافذة تحذّرك بعدم إمكانية التراجع، وتُرفض المحاولة بلا سبب برسالة «يرجى كتابة سبب الرفض».
سبب الرفض يُكتب في حقل نصّه التمهيدي «اكتب سبب واضح سيظهر للمتقدم…» ويُرسل ضمن `{ rejectReason }` ليستقر على صف الطلب نفسه.

في الخلفية تُنفَّذ المعاملة المذكورة في قسم الأدوار: تحديث الحساب وتحديث الطلب معاً، ثم قيد حدث في سجل التدقيق باسم المدير وعنوانه.
طلب مُعالَج سابقاً يرد بخطأ «لا يمكن تعديل طلب مُعالَج»، فلا تكرار للاعتماد.
الرفض الافتراضي للسبب الفارغ هو «تم رفض الطلب» كما في الكود.

### مراجعة الورش `/admin/workshops/review`

العنوان «مراجعة الورش»، ولها أربعة تبويبات: «ورش بانتظار المراجعة» و«كل الورش» و«إعلانات الورش» و«البلاغات».
تحت التبويب فلاتر حالة: «الكل» و«موثقة» و«محظورة» و«موقفة»، مع بحث نصي له نص «ابحث عن ورشة...».
كل عملية تجلب بياناتها من مسار مختلف: التبويبان الأول والثاني من `GET /api/admin/workshops`، والإعلانات من `GET /api/admin/workshops/ads`، والبلاغات من `GET /api/admin/workshops/reports`، وكلها بمعاملات `page` و`status` و`search`.

الإجراءات على الورشة تشمل القبول والرفض والحظر والإيقاف والحذف، وأزرارها مثل «حظر الورشة» و«إلغاء الحظر» و«إيقاف» و«إلغاء الإيقاف».
الرفض والحظر يستدعيان نافذة سبب، وحقل الحظر نصّه «أدخل سبب الحظر...» وحقل الرفض «أدخل سبب الرفض...».
مدد الحظر المتاحة خمس: «يوم واحد» و«3 أيام» و«أسبوع» و«شهر» و«دائم».

الطلبات تُرسل بـ `POST /api/admin/workshops` مع جسم `{ action }`، والإعلانات عبر `POST /api/admin/workshops/ads`، والبلاغات عبر `POST /api/admin/workshops/reports`.
إخفاء الورشة أو حظرها يعيد تحديث القائمة فوراً، وأي فشل يظهر كرسالة خطأ من السيرفر داخل النافذة.

### الحارس الأمني `/admin/sentinel`

العنوان «الحارس الأمني (Sentinel)» ووصفه «مراقبة تلقائية للسلوك المشبوه»، مع سطر يبيّن الوضع الحالي: «مراقبة (بدون حظر)» أو «تفعيل (حظر تلقائي)» أو «موقوف طوارئ».
أزرار التحكم ثلاثة فقط: «مراقبة» و«تفعيل الحظر» و«إيقاف طوارئ» (أو «إعادة التشغيل»)، وكلها تطلب تأكيداً مزدوجاً ثم `POST /api/admin/sentinel` وتعرض «تم الحفظ».
بطاقات الإحصاء تقيس «حظر تلقائي (24h)» و«كان سيُحظر (مراقبة)» وعدّاداً لكل نوع إشارة.

جدول الإشارات أعمدته: النوع، المستخدم، التفاصيل، IP، الوزن، الوقت، مع فلتر «كل الأنواع» وعدّاد «إجمالي الإشارات» وترقيم صفحات «صفحة 1 من N».
أسماء الأنواع كما تظهر: «سبام إعلانات» و«سبام رسائل» و«تخمين دخول» و«بلاغات ضده» و«محاولة دخول الإدارة» و«طرق باب الإدارة (زائر)» و«مسار فخ» و«تجاوز معدل».
رسالة الحالة عند الهدوء: «لا إشارات — الوضع هادئ». التفاصيل الكاملة للأوزان والعتبات في القسم السادس.

### النسخ الاحتياطية `/admin/backups`

وصف الصفحة: «نسخة تلقائية كل 5 ساعات تُرسل للبريد + إشعار واتساب — مع نسخ يدوية محفوظة».
الزر الرئيسي «نسخ احتياطي الآن» (ويصبح «جاي النسخ...» أثناء العمل) بجانب زر «تحديث».
أربع بطاقات حالة: «آخر نسخة» مع نوعها «تلقائية» أو «يدوية»، و«نسخ محفوظة» مع «احتفاظ بآخر 10 تلقائية»، و«قاعدة البيانات الآن» بعدد السجلات والجداول، و«الجدولة التلقائية» التي تقول «مفعّلة كل 5 ساعات» و«إيميل + واتساب تلقائي» أو «حدّد BACKUP_CRON_SECRET».

جدول «النسخ المحفوظة» يعرض الملف والنوع والحجم وعدد الجداول/السجلات وحالة الإيميل وحالة الواتساب والتاريخ، مع إجراءي «تنزيل» و«حذف» لكل صف.
زر «استدعاء نسخة (استيراد)» يقبل ملف `.json` ويعرض «تم الاستيراد» أو «ملف غير صالح».
التفاصيل التقنية لآليات النسخ الثلاث ومواعيد التشغيل في القسم السابع.

### الإعدادات `/admin/settings`

العنوان «إعدادات الموقع» ووصفه «التحكم الكامل بإعدادات ومحتوى الموقع»، وله ستة تبويبات: «عام» و«المظهر» و«الصفحة الرئيسية» و«أنواع الوقود» و«الفئات» و«إدارة المحتوى».
زر «حفظ جميع الإعدادات» (ويصبح «جاري الحفظ...») يرسل كل الحقول دفعة واحدة عبر `PUT /api/admin/settings` بجسم `FormData`، ويعرض «تم حفظ الإعدادات».
رفع الشعار حدث مستقل بنفس المسار ورسالته «تم رفع الشعار»، والتفاصيل الكاملة للحقول والتبويبات في القسم الثامن.

### صفحات البلاغات والمراجعة

**`/admin/reports` — البلاغات.** عنوانها «البلاغات»، وتحمل بياناتها من `GET /api/admin/reports?status=...` مع فلتر حالة.
لكل بلاغ أربعة أزرار بعناوينها التلميحية: «حل البلاغ» و«رفض البلاغ» و«عرض الإعلان» و«حذف».
النجاح يعرض «تم حل البلاغ» أو «تم رفض البلاغ» أو «تم حذف البلاغ»، والحذف يمر بتأكيد «هل أنت متأكد من حذف البلاغ؟».

**`/admin/car-comment-reports` — بلاغات تعليقات السيارات.** عنوانها «بلاغات تعليقات السيارات».
تدعم الحل والرفض والحذف النهائي، إضافة إلى حظر صاحب التعليق بمدد: «دون حظر» و«30 دقيقة» و«ساعة» و«ساعتين» و«يوم» و«3 أيام» و«أسبوع» و«أسبوعين» و«شهر» و«دائم».
المطلوب `/api/admin/car-comment-reports` للبلاغات و`/api/admin/car-comment-users/[id]/ban` للحظر.

**`/admin/forum-reports` — بلاغات المنتدى.** عنوانها «بلاغات المنتدى».
الإجراءات: حل ورفض وحذف بلاغ، إضافة إلى حظر المستخدم عبر `/api/admin/forum-users/[id]/ban`.
مدد الحظر هنا: «دون حظر» و«ساعة» و«6 ساعات» و«يوم» و«3 أيام» و«أسبوع» و«أسبوعين» و«شهر» و«دائم».

**`/admin/sounds` — بلاغات الصوت.** عنوانها «إدارة بلاغات الصوت» ووصفها «مراجعة البلاغات وإدارة الحظرات».
تجلب البلاغات من `/api/sounds/reports?status=...` والحظرات من `/api/sounds/bans`، وتعرض تسجيلات السيارة عبر `/api/cars/[id]/sounds`.
سبب الإجراء نصّه التمهيدي «مثال: محتوى مخالف» مع حقل رسالة توضيحية، والحظر يُرسل إلى `/api/sounds/bans`.

**`/admin/premium-requests` — الطلبات المميزة.** عنوانها «الطلبات المميزة» وفلاترها «معلق» و«مقبول» و«مرفوض» و«الكل».
أنواع الطلب تظهر بشارة «تمييز» لـ `FEATURE` أو «تثبيت» لـ `PIN`، والقرار عبر `POST /api/admin/premium-requests` بقبول أو رفض ورسالتي نجاح «تم قبول الطلب» و«تم رفض الطلب».

**`/admin/workshops` — إدارة الورش.** عنوانها «إدارة الورش» وتبويباتها «كل الورش» و«بانتظار التوثيق» و«محظورة» و«موقفة».
إجراءاتها: توثيق، حظر («أدخل سبب الحظر...»)، إيقاف («أدخل سبب الإيقاف...»)، وحذف الورشة عبر `DELETE /api/admin/workshops?workshopId=...`.
هذه الصفحة بلا فحص دور في الواجهة العميلة، وقد سبق التنبيه عليه في أول الفصل.

**`/admin/workshops/ads` — إعلانات الورش.** عنوانها «إدارة إعلانات الورش».
لها ثلاثة تبويبات رئيسية: «إعلانات الورش» و«إدارة الورش» و«بلاغات الورش».
حالات الإعلان: «الكل» و«قيد المراجعة» و«منشورة» و«مرفوضة»؛ حالات الورش: «الكل» و«موثقة» و«غير موثقة» و«موقفة» و«محظورة»؛ حالات البلاغ: «قيد المراجعة» و«تم الحل» و«تم التجاهل» و«الكل».

### صفحات المحتوى والمقالات

**`/admin/articles` — المقالات والأخبار.** عنوانها «المقالات والأخبار»، وتحمّل حتى 100 مقال من `GET /api/articles?limit=100&all=true`.
الحذف الفردي يمرّ بـ `DELETE /api/articles/[slug]` بعد تأكيد «حذف المقال؟»، وهناك زر «حذف الكل» يحاول `DELETE /api/articles` بلا جسم وهو ما يفشل كما سيُشرح في آخر الفصل.

**`/admin/articles/add` — إضافة مقال جديد.** عنوانها «إضافة مقال جديد»، وحقولها: العنوان والمحتوى (إلزاميان برسالة «العنوان والمحتوى مطلوبان») ورابط الصورة والوسوم (مثال: «سيارات, أردن, 2026») وملخص قصير.
تلميح المحرر: «اكتب المحتوى هنا... استخدم ## للعناوين الفرعية»، والنشر عبر `POST /api/articles` ثم الانتقال إلى قائمة المقالات.

**`/admin/articles/[id]` — تعديل المقال.** عنوانها «تعديل المقال»، وتحمّل المقال من `GET /api/articles/[id]` وتحفظ عبر `PUT` على المسار نفسه، ورسالة النجاح «تم الحفظ».

**`/admin/content-tools` — المحتوى الذكي.** عنوانها «إدارة المحتوى بالذكاء الاصطناعي».
تختار سيارة معتمدة من قائمة، أو تكتب معرّفها يدوياً في حقل بتلميح «أو أدخل ID السيارة...».
زران: توليد وصف يعرض «تم إنشاء الوصف»، وكشف الصور المكررة، والتنفيذ عبر `POST /api/admin/content-tools`.

**`/admin/tags` — وسوم السيارات.** عنوانها «إدارة وسوم السيارات»، وحقولها «الاسم بالعربية» (مثال: «مميزة») و«الاسم بالإنجليزية» (مثال: `Featured`) و`slug` (مثال: `featured`).
الإنشاء والتعديل عبر `POST/PUT`، والحذف عبر `DELETE /api/admin/tags/[id]`، والتفعيل والتعطيل عبر مسار PATCH مع رسالتي «تم إيقاف الوسم» و«تم تفعيل الوسم».

**`/admin/parts` — قطع الغيار.** عنوانها «إدارة قطع الغيار»، وتحمل بياناتها من `GET /api/admin/parts` مع فلتر حالة يبدأ بـ «الكل».
التحديث عبر `PUT /api/admin/parts/[id]` ورسالته «تم التحديث»، والحذف عبر `DELETE` بعد تأكيد «حذف القطعة نهائياً؟».

### صفحات البيانات المرجعية

**`/admin/brands` — الشركات.** عنوانها «الشركات» ووصفها «إدارة شركات السيارات»، والنافذة تطلب الاسم بالعربية والإنجليزية.
الإنشاء والتعديل عبر `POST/PUT` و`/api/admin/brands`، والحذف عبر `DELETE` بنفس المسار مع جسم `{ id }`، ورسائل النجاح «تمت الإضافة» و«تم التحديث» و«تم الحذف».

**`/admin/models` — الموديلات.** عنوانها «الموديلات» ووصفها «إدارة موديلات السيارات».
تُحمّل مع قائمة الشركات دفعة واحدة، ولا يقبل الحفظ بدون اسم وشركة (رسالة «الاسم والشركة مطلوبان»)، والمسارات `/api/admin/models` و`/api/admin/brands`.

**`/admin/cities` — المدن والمناطق.** عنوانها «المدن والمناطق»، وتحمل المحافظات والمدن معاً لتربط كل مدينة بمحافظتها.
الحقول «الاسم بالعربية» و«English name»، والحذف يمر بتأكيد «حذف المدينة؟»، والمسارات `/api/admin/cities` و`/api/admin/cities/[id]`.

**`/admin/provinces` — المحافظات.** عنوانها «المحافظات»، وفيها زر لإضافة البناء الكامل يعرض «تم إضافة N محافظات وM مدينة».
الإضافة الفردية والتعديل عبر `/api/admin/provinces` والحذف عبر `/api/admin/provinces/[id]` بعد تأكيد «حذف المحافظة؟».

**`/admin/forum-categories` — أقسام المنتدى.** عنوانها «أقسام المنتدى»، وحقولها الاسم بالعربية والإنجليزية و`slug` (تلميح: `q-a`)، والحفظ بلا اسم يرد بـ «الاسم وال slug مطلوب».
الحذف نهائي بعد تأكيد «حذف القسم نهائياً؟»، والمسارات `/api/admin/forum-categories` و`/api/admin/forum-categories/[id]`.

**`/admin/plans` — الباقات.** عنوانها «الباقات»، والحقول تشمل «نظام (System Name)» بتلميح «مثال: SILVER» والسعر والمدة والفعالية.
مزايا الباقة تحدَّد بخمسة مفاتيح: «شارة مميزة» و«ظهور في أول القائمة» و«ظهور في الصفحة الرئيسية» و«ترويج في وسائل التواصل» و«دعم VIP».
الإنشاء والتعديل عبر `/api/admin/plans` والحذف عبر `/api/admin/plans/[id]` بعد تأكيد «هل أنت متأكد من حذف هذه الباقة؟».

**`/admin/badges` — نظام الشارات.** عنوانها «نظام الشارات»، والنافذة تحمل حقل اسم بتلميح «مثال: بائع موثوق».
الإنشاء والتعديل عبر `/api/admin/badges`، والحذف عبر `/api/admin/badges/[id]`، والتفعيل والتعطيل عبر PATCH مع رسالتي «تم التفعيل» و«تم التعطيل».
هذه الشارات هي نفسها التي تُدار من نافذة شارات المستخدم في `/admin/users`.

### صفحات التحليلات والدعم

**`/admin/advanced-stats` — الإحصائيات المتقدمة.** عنوانها «الإحصائيات المتقدمة» ووصفها «رسوم بيانية وتحليلات متقدمة للسوق» مع زر «تحديث البيانات».
المصدر `GET /api/admin/advanced-stats`، ومؤشراتها: «إجمالي الإعلانات» و«مستخدمون جدد (آخر شهر)» و«إعلانات جديدة (آخر شهر)» و«الأكثر طلباً» و«أنشط محافظة».
الرسوم تشمل «أكثر الماركات طلباً» و«توزيع الأسعار» و«نشاط المستخدمين (آخر 6 أشهر)» وتوزيعات المدن والوقود والسنوات.

**`/admin/audit-logs` — سجل النشاطات.** عنوانها «سجل النشاطات»، وتقرأ من `GET /api/admin/audit-logs` مع بحث «ابحث بالاسم أو البريد الإلكتروني...».
فلاتر النوع خمسة: «الكل» و«المستخدمون» و«السيارات» و«التعليقات» و«الدخول والخروج».
كل سطر يوثّق الفاعل والإجراء والكيان والوقت وعنوان IP، وهو المرجع عند أي شكوى.

**`/admin/seller-reports` — تقرير أداء البائعين.** عنوانها «تقرير أداء البائعين»، وبحثها «بحث باسم التاجر أو البريد...».
المصدر `GET /api/admin/seller-reports`، وهو يحصر النتائج بحسابات `DEALER` فقط.
لكل تاجر: عدد السيارات المنشورة والمباعة والنشطة، والرسائل المرسلة والمستلَمة، والتقييمات وعدد المراجعات.

**`/admin/tickets` — التذاكر.** عنوانها «التذاكر»، وفلاتها «الكل» و«مفتوحة» و«قيد المعالجة» و«تم الحل» و«مغلقة».
القراءة من `GET /api/admin/tickets`، والرد على التذكرة عبر `PUT /api/tickets/[id]` بحقل «اكتب رداً...» حدّه 2000 حرف، ورسالة النجاح «تم إرسال الرد».
الإجراءات الإدارية (إسناد وإغلاق وحذف) عبر `POST /api/admin/tickets`، والحذف يتطلب تأكيداً: «هل أنت متأكد من حذف هذه التذكرة؟».

**`/admin/messages` — الرسائل.** عنوانها «الرسائل (الإدارة)»، وتحمّل قائمة المحادثات من `/api/admin/conversations` مع بحث نصي.
فتح المحادثة يجلب رسائلها من `/api/admin/conversations/[id]`، والإرسال بحقل «اكتب رداً من الإدارة...» ورسالة «تم الإرسال».
الاستخدام المقصود مراقبة الحوارات والتدخل نيابة عن الإدارة، لا المراسلة اليومية.

**`/admin/subscriptions` — الاشتراكات.** عنوانها «الاشتراكات»، وبحثها «ابحث بالاسم أو البريد الإلكتروني...».
الإجراءات: تفعيل أو تعطيل الاشتراك، والتمديد (عدد الأيام من 1 إلى 365 وإلا «عدد أيام غير صالح (1-365)»)، والحذف النهائي بعد تأكيد.
المسارات `GET /api/admin/subscriptions` و`PUT/DELETE /api/admin/subscriptions/[id]`، وكل نجاح يعيد تحميل القائمة.

**`/admin/fair-price` — مؤشر عدالة السعر.** عنوانها «مؤشر عدالة السعر».
`GET /api/admin/fair-price` يعيد العدد الكلي للإعلانات المعتمدة وعدد المقدَّرة وغير المقدَّرة، مع العتبتين `belowMarket: -8` و`aboveMarket: 8`.
زر إعادة الحساب ينفّذ `POST /api/admin/fair-price` مباشرة ويعرض «تم إعادة حساب N سيارة»، ثم يعيد جلب الأرقام بطلب `GET` جديد.

## الحارس الأمني Sentinel والسجلات والتقارير

### كيف يفكر الحارس

الحارس مكتوب في `src/lib/sentinel.ts`، وفكرة عمله بسيطة: كل سلوك مشبوه يضيف «وزناً» إلى حساب المستخدم خلال نافذة 24 ساعة، وعند تجاوز العتبة يُنفَّذ الحظر.
الأوزان الحقيقية كما هي في `SIGNAL_WEIGHTS`:

| الحدث | الوزن | الشرط المكتوب في الكود |
|---|---|---|
| `SPAM_LISTING` | 8 | بعد 5 إعلانات في الساعة |
| `SPAM_MESSAGE` | 5 | بعد 10 رسائل في 5 دقائق |
| `BRUTE_FORCE` | 15 | عند 5 محاولات دخول فاشلة (+25 عند 10) |
| `ABUSE_REPORTS` | 20 | ثالث بلاغ معلّق على إعلاناته (+40 عند الخامس) |
| `ADMIN_PROBE` | 100 | محاولة دخول `/admin` لغير مدير |
| `ADMIN_PROBE_GUEST` | 1 | زائر يطرق `/admin` — للأدلّة فقط ولا يحظر |
| `HONEYPOT` | 15 | لمس مسارات مثل `/wp-admin` و`/.env` و`/.git` |
| `RATE_ABUSE` | 5 | تجاوز معدل الطلبات المسموح |

### العتبات والحِجَم

ثلاثة أرقام تحكم كل شيء: `TEMP_THRESHOLD = 30` و`PERM_THRESHOLD = 60` و`TEMP_BAN_MS` = 24 ساعة.
إذا بلغ مجموع النقاط 30 فأكثر خلال يوم يُفرض حظر مؤقت 24 ساعة، وإذا بلغ 60 أو كان للمستخدم حظر سابق خلال النافذة تحوَّل الحظر إلى دائم.
محاولة دخول لوحة الإدارة من حساب غير مدير تُعامل استثناءً: تُسجَّل إشارة `ADMIN_PROBE` بوزن 100 وتُفرض مباشرة مدة 7 أيام (`PROBE_BAN_MS`) عبر `SENTINEL_PROBE_BAN`.
المدراء لا يُحظرون تلقائياً أبداً، وكل حظر أو «كاد يُحظر» يُقيَّد في سجل التدقيق بأفعال `SENTINEL_BAN` و`SENTINEL_WOULD_BAN` و`SENTINEL_PROBE_BAN`.

```ts
const TEMP_THRESHOLD = 30;
const PERM_THRESHOLD = 60;
const TEMP_BAN_MS = 24 * 60 * 60 * 1000;
const PROBE_BAN_MS = 7 * 24 * 60 * 60 * 1000;
```

> اختلاف بين الصفحة والكود: بطاقة «قواعد الحارس» في `/admin/sentinel` تكتب «الأوزان: سبام إعلانات 8، سبام رسائل 5، تخمين دخول 15، بلاغات 20، فخ 15»، ولا تذكر `ADMIN_PROBE` بوزن 100 ولا `ADMIN_PROBE_GUEST` بوزن 1 ولا `RATE_ABUSE` بوزن 5. اعتمد دائماً جدول `SIGNAL_WEIGHTS` في `src/lib/sentinel.ts`.

### الوضع والتحكم

الوضعان العاملان `monitor` و`enforce`: الأول يسجّل فقط («كان سيُحظر (مراقبة)»)، والثاني يحظر فعلياً.
زر «إيقاف طوارئ» يوقف كل الحظر التلقائي فوراً ويتحوّل إلى «إعادة التشغيل»، والتأكيد ينص على «إيقاف طوارئ: يوقف كل الحظر التلقائي فوراً؟».
القراءة عبر `GET /api/admin/sentinel?page=1&limit=30&type=...` والكتابة عبر `POST /api/admin/sentinel` بأجسام `{ mode }` أو `{ stopped }`.

```http
GET /api/admin/sentinel?page=1&limit=30&type=ADMIN_PROBE
Authorization: Bearer <admin-token>
```

### السجلات والتقارير المرتبطة

سجل التدقيق من صفحة `/admin/audit-logs` يقرأ `GET /api/admin/audit-logs` ويستعمل الفلاتر الخمسة المذكورة سابقاً، وهو مرجع تتبّع كل تغيير.
التقارير التشغيلية موزّعة: الإحصائيات المتقدمة من `GET /api/admin/advanced-stats`، وأداء البائعين من `GET /api/admin/seller-reports`، ومؤشر عدالة السعر من `GET /api/admin/fair-price`.
التقرير الأسبوعي يُولَّد آلياً من `src/app/api/cron/weekly-report` كل أحد الساعة 04:00 حسب `vercel.json`.

## النسخ الاحتياطية

### الآلية الأولى: تصدير واستيراد JSON

`GET /api/admin/backup` يعيد إحصاء كل جدول من قائمة `MODELS` (عدد الجداول وعدد السجلات)، وهو مصدر بطاقة «قاعدة البيانات الآن».
`POST /api/admin/backup` مع `{ "action": "export" }` يبني ملف JSON بإصدار `version: '1.0'` يحوي كل الجداول، مع إسقاط حقول حساسة من `SENSITIVE_FIELDS`: `password` و`lastLoginIp` و`failedLoginAttempts` و`lockedUntil`.
الاستيراد يمرّ بنفس المسار بجسم `{ "action": "import" }`، والزر في الواجهة هو «استدعاء نسخة (استيراد)» ويقبل ملفات `.json` فقط.
هذه هي الآلية الوحيدة التي تسمح بالانتقال بين قواعد بيانات مختلفة، لأنها لا تمسّ ملف القاعدة مباشرة.

### الآلية الثانية: نسخة ملف القاعدة

`POST /api/admin/backup/run` يستدعي `runBackup({ type: 'MANUAL' })` من `src/lib/backup.ts`، فينسخ ملف SQLite `prisma/dev.db` إلى مجلد `backups/` باسم بتوقيت لحظة التنفيذ، ثم يسجّل حدث `BACKUP_CREATED` في التدقيق.
`GET /api/admin/backup/run` يعيد آخر 50 نسخة مسجَّلة، وهي نفسها التي تظهر في جدول «النسخ المحفوظة».
`POST /api/admin/backup/auto` ينفّذ النسخة التلقائية ويحتفظ بآخر 10 ملفات `auto-backup-*` فقط (ثابت `MAX_AUTO_KEEP = 10`)، ثم يحذف الزائدة وفق العمر أيضاً (`RETENTION_DAYS` افتراضها 14 يوماً وقابلة للضبط عبر `BACKUP_RETENTION_DAYS`).
تنزيل نسخة عبر `GET /api/admin/backup/[filename]` وحذفها عبر `DELETE` على المسار نفسه، مع مزامنة حذف سجل القاعدة.

### الآلية الثالثة: الجدولة التلقائية

`src/app/api/cron/backup/route.ts` يستقبل نداء `POST` من مجدول خارجي كل 5 ساعات، ويُرفض إن لم يوجد `BACKUP_CRON_SECRET` مطابق في متغيرات البيئة (وإذا لم يُضبط أصلاً يرد بـ 503).
`GET` على المسار نفسه يوفّر حالة الجدولة للتشخيص ويعيد `{ "schedule": "every 5 hours", "enabled": true }`، ولا يكشف شيئاً حسّاساً.
نص ترويسة الصفحة يشرح النتيجة العملية: نسخة تلقائية كل 5 ساعات تُرسل للبريد مع إشعار واتساب.

```bash
curl -X POST https://your-domain/api/cron/backup \
  -H "Authorization: Bearer $BACKUP_CRON_SECRET"
```

### قنوات التسليم والحدود

البريد يُرسل كل نسخة كمرفق حتى 20MB (حد `EMAIL_ATTACH_LIMIT` لأن Gmail يرفض الأكبر)، ويتطلب `SMTP_USER` و`SMTP_PASS` في البيئة.
بطاقة البريد تُظهر وجهة الاستقبال الثابتة في الكود، وبطاقة الواتساب تقول إن الإشعار يصل بالساعة والثواني وتاريخ اليوم بتوقيت عمّان.
تقرير حالة البطاقة يوضّح أنه إن لم يُضبط `BACKUP_CRON_SECRET` تظهر «غير مفعّلة» مع تلميح «حدّد BACKUP_CRON_SECRET».
يوجد أيضاً `backupEncryptionStatus()` في `src/lib/backup.ts` يبيّن حالة تشفير النسخ والنص التوضيحي المرتبط بها.
ملاحظة: `vercel.json` لا يحوي مجدول النسخ الاحتياطي، فالآلية التلقائية تعتمد على مناداة `/api/cron/backup` من مجدول خارجي، لذلك فإن تعطيل ذلك المجدول يوقف النسخ التلقائي دون أي أثر ظاهر في اللوحة.

## الإعدادات العامة

### التبويب «عام»

أول عنوان داخله «الإعدادات العامة»، وحقوله: اسم الموقع بالعربية والإنجليزية، العملة، رمز العملة، ونسبة الضريبة (%) برقم عشري.
ثم قسم «معلومات الاتصال»: البريد الإلكتروني، رقم الهاتف، العنوان.
ثم «تحسين محركات البحث (SEO)»: وصف الموقع والكلمات المفتاحية.
وأخيراً «صيانة الموقع»: مفتاح «تفعيل وضع الصيانة»، وعند تفعيله يظهر حقل «رسالة الصيانة»، ويُحفظ مع بقية الحقول في نفس النداء.

### التبويب «المظهر»

قسم «الشعار» يعرض الشعار الحالي أو أيقونة فارغة وزر «رفع الشعار»، والرفع حدث مستقل على `PUT /api/admin/settings` بملف واحد ورسالة «تم رفع الشعار».
قسم «الألوان» يضم ثلاثة حقول: «اللون الأساسي» و«اللون الثانوي» و«لون التمييز»، لكل منها منتقي لون وحقل نصّي للقيمة الست عشرية.

### التبويب «الصفحة الرئيسية»

حقول النص: «عنوان القسم الرئيسي (Hero)» و«النص الفرعي».
قسم «إظهار الأقسام» أربعة مفاتيح: «إظهار السيارات المميزة» و«إظهار قسم المحافظات» و«إظهار قسم الشركات» و«إظهار الإحصائيات».
قيمها المنطقية تُقرأ بشرط `!== false`، أي أن الغياب في قاعدة البيانات يعني «مفعّل».

### التبويبان «أنواع الوقود» و«الفئات»

التبويب الأول عنوانه «أنواع الوقود» وحقله «أدخل نوع الوقود...» وزر «إضافة»، والثاني عنوانه «فئات السيارات» وحقله «أدخل الفئة...».
كل عنصر يظهر كشارة قابلة للحذف بعلامة X، والقيمة تُخزَّن كسلسلة JSON في حقل واحد.
إضافة عنصر مكرر تُرفض برسالة «موجود مسبقاً»، وإدخال القيمة يتحوّل تلقائياً إلى أحرف كبيرة.

### التبويب «إدارة المحتوى»

ليس نموذجاً بل ست بطاقات روابط: «المحافظات» و«الشركات» و«الموديلات» و«الباقات» و«الاشتراكات» و«الشارات»، ولكل منها وصف قصير ينقلك مباشرة إلى صفحتها.

### الحفظ والتحقق

زر «حفظ جميع الإعدادات» يبني `FormData` ويضمّ الحقول النصية فقط: `siteName` و`siteNameAr` و`metaDescription` و`metaKeywords` و`currency` و`currencyAr` و`taxPercent` و`contactEmail` و`contactPhone` و`address` و`socialMedia` و`maintenance` و`maintenanceMessage` و`primaryColor` و`secondaryColor` و`accentColor` و`homeHeroTitle` و`homeHeroSubtitle` و`homeShowFeatured` و`homeShowCities` و`homeShowBrands` و`homeShowStats` و`fuelTypes` و`bodyTypes`.
الإرسال بـ `PUT /api/admin/settings` مع ترويسة المدير فقط، والنجاح «تم حفظ الإعدادات» والفشل «فشل الحفظ».

```ts
const fd = new FormData();
fd.append('siteNameAr', 'JO Cars');
fd.append('maintenance', 'true');
fd.append('maintenanceMessage', 'أثناء التحديث، نعود بعد قليل');
await fetch('/api/admin/settings', {
  method: 'PUT',
  headers: { Authorization: `Bearer ${token}` },
  body: fd,
});
```

> لاحظ أن وضع الصيانة هنا يُدار عبر إعدادات الموقع، بينما يوجد مسار مستقل لـ `PUT /api/admin/maintenance` لا تستدعيه أي واجهة، وهو مذكور في القسم الأخير.

## ملاحظات وثغرات مرصودة

1. **مسارات API بلا واجهة.** المسارات `src/app/api/admin/security/route.ts` (إحصاءات أمنية و IPs محظورة) و`src/app/api/admin/car-logs/route.ts` و`src/app/api/admin/valuations/intelligence/route.ts` و`PUT /api/admin/maintenance/route.ts` موجودة ومحمية، لكن لا يستدعيها أي ملف واجهة في المشروع.
2. **رابط وهمي في قاعدة معرفة الموقع.** الملف `src/ai/site-knowledge.ts` يعرِّف بطاقة «إدارة المنتدى» على المسار `/admin/forum`، وهذه الصفحة غير موجودة فعلياً؛ المسارات الصحيحة هي `/admin/forum-categories` و`/admin/forum-reports`.
3. **زر «حذف الكل» في المقالات لا يعمل.** الصفحة تنفّذ `DELETE /api/articles` بلا جسم، بينما يطلب المسار مصفوفة `ids` غير فارغة وبحد أقصى 50 مقالاً، فتصدّر دائماً برسالة خطأ.
4. **بطاقة «الإيرادات» تعرض صفراً دائماً.** مسار `GET /api/admin/stats` يعيد `revenue: 0` حرفياً بدل حساب الإيرادات، فقيمة `${stats.revenue} د.أ` ثابتة.
5. **مسارات قراءة عامة تحت بادئة الإدارة.** `GET` في `/api/admin/brands` و`/api/admin/models` و`/api/admin/cities` و`/api/admin/provinces` لا يطلب توثيقاً، بينما عمليات الكتابة عليهم محمية بالمدير. إن كان قصد البادئة سرية كاملة فهذه خلل في الفصل.
6. **غياب فحص دور في صفحة إدارة الورش.** `src/app/admin/workshops/page.tsx` لا يحتوي شرط `user?.role !== 'ADMIN'`، فتُعرض الصفحة الفارغة لغير المدير بدل إعادة توجيهه، مع بقاء البيانات محمية برد `401`.
7. **تعارض بسيط بين نص الواجهة والكود في الحارس.** بطاقة القواعد تذكر خمسة أوزان فقط بينما `SIGNAL_WEIGHTS` يحوي ثمانية، كما هو مفصّل في قسم الحارس.
8. **جدولة النسخ خارج `vercel.json`.** المجدول اليومي يضم `recalculate` و`weekly-report` و`news-aggregator` فقط، والنسخ الاحتياطي يعتمد على مناداة `/api/cron/backup` بسر `BACKUP_CRON_SECRET`.

> قبل الاعتماد على أي ميزة في هذا الفصل، تحقّق من اسم المسار في `src/app/api/admin/` مباشرة؛ فبعض الأزرار القديمة تستدعي مسارات حُذف أو تغيّر شكل جسمها، وأشهرها زر «حذف الكل» في المقالات.
