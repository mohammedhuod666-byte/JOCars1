# الفصل الخامس: لوحة التاجر والمعرض ولوحة الورشة

هذا الفصل يشرح واجهات الطرف الثالث في JO Cars: حساب التاجر ولوحته التفصيلية، وصفحة المعرض العامة، ولوحة صاحب الورشة ومساراتها العامة.
كل اسم عربي وكل رقم في هذا الفصل مأخوذ من الكود الفعلي في `src/components/dealer/` و`src/app/dealer/` و`src/app/workshops/` و`src/app/profile/` ومسارات `src/app/api/` المقابلة.
لا يوجد في هذا الفصل وصف مبني على التخمين: ما لم يُذكر في الكود صراحة — كأرقام تجريبية — ذُكر بأنه كذلك.

## مَن يُعدّ تاجراً؟

### الأدوار الأربعة وكيف تكتسبها

النظام يعرف أربعة أدوار فقط: `USER` و`TRADER` و`DEALER` و`ADMIN`، وهي معروضة في `src/lib/enums.ts`.
صفحة التسجيل `src/app/auth/register/page.tsx` تضع في أعلى النموذج مبدّلاً من ثلاثة خيارات: «مستخدم» و«تاجر سيارات» و«معرض».

| الخيار في التسجيل | الدور المكتوب | ماذا يحدث فوراً |
|---|---|---|
| مستخدم | `USER` | حساب عادي، لا يحتاج أي اعتماد |
| تاجر سيارات | `TRADER` | يُسجَّل الدخول مباشرة و`dealerVerified = false` |
| معرض | `DEALER` | حساب معرض قديم الطراز، ويعتبر «تاجر مميّز» في إدارة المستخدمين |

عند اختيار «تاجر سيارات» تظهر ملاحظة صريحة تحت المبدّل: «حساب التاجر يتيح لك عرض معرضك وسياراتك. سيتم مراجعة طلبك واعتماده من الإدارة خلال 24 ساعة.»
في الخادم يقبل `POST /api/auth/register` الحقول `dealerName` و`dealerDescription` و`dealerAddress` و`dealerLogo` و`commercialReg` ويخزنها فوراً، ثم يرسل إشعاراً للمديرين: «تاجر جديد سجّل بنفسه: الاسم (البريد) — يحتاج اعتماد الإدارة لتفعيل استقبال الحجوزات».

> ملاحظة: التسجيل كتاجر لا يفتح كل شيء تلقائياً. الحساب يبقى `dealerVerified = false` حتى تتوثق الإدارة، وعندها فقط تُفعَّل ميزات الستوري ولوحة الحجوزات.

### دورة التوثيق الكاملة خطوة بخطوة

الدورة تمر بأربع محطات: الطلب من لوحة التاجر، ثم مراجعة الإدارة، ثم الاعتماد بمعاملة واحدة، ثم انعكاس ذلك على الحساب.

1. افتح لوحة التاجر، وستجد شارة تحذير كهرمانية: «حسابك غير موثّق — وثّق معرضك لزيادة ثقة المشترين».
2. اضغط «طلب توثيق الحساب»، واملأ حقل الملاحظات الذي يحمل النص الإرشادي: «ملاحظات للإدارة (اختياري): السجل التجاري، العنوان التفصيلي، سنوات الخبرة...».
3. اضغط «إرسال الطلب»، فتُرسل المعطيات إلى `POST /api/trader/verification`.
4. تتحول الشارة إلى «طلب التوثيق قيد مراجعة الإدارة — سيتم إشعارك عند الاعتماد».
5. يراجع المدير الطلب من `/admin/traders-approval` ويضغط «اعتماد» أو «رفض» مع سبب إلزامي.

### واجهة الطلب: `POST /api/trader/verification`

- **المصادقة:** ترويسة `Authorization: Bearer` متبوعة بالتوكن، والدور المسموح به `TRADER` أو `DEALER` أو `ADMIN` فقط.
- **حقول الطلب:** حقل اختياري واحد `notes` (ملاحظات)، ويُقتطع إلى 1000 حرف كحد أقصى.
- **سلوك النسخ:** ينسخ الخادم من ملف الحساب `dealerName` و`dealerLogo` و`dealerDescription` و`dealerAddress` و`commercialReg` إلى صف الطلب تلقائياً.
- **الرد:** `201` مع `{ request: { id, status: "PENDING", createdAt } }`.
- **الردود المحظورة:** `403` «طلب التوثيق متاح لحسابات التجار فقط»، و`400` «حسابك موثّق مسبقاً»، و`400` «لديك طلب توثيق معلّق قيد المراجعة»، و`429` «لقد أرسلت عدة طلبات — حاول لاحقاً».

الحدّ المضاد للتكرار مضمّن في المسار نفسه: ثلاث محاولات فقط لكل ساعة لكل مستخدم.

```ts
const rateLimit = checkRateLimit(`verify-req:${user.id}`, {
  windowMs: 60 * 60 * 1000, // ساعة واحدة
  maxRequests: 3,           // 3 طلبات كحد أقصى
});
if (!rateLimit.allowed) return errorResponse('لقد أرسلت عدة طلبات — حاول لاحقاً', 429);
```

بعد الإنشاء يُشعَر المكتب كله عبر `notifyAdmins('TRADER_VERIFICATION', 'طلب توثيق تاجر جديد', ...)` ويُختم في سجل التدقيق بفعل `TRADER_REQUEST`.

### قراءة الحالة: `GET /api/trader/verification`

المسار نفسه يدعم القراءة بدون حقول طلب، ويعيد:

```json
{
  "success": true,
  "data": {
    "request": { "id": "…", "status": "PENDING", "rejectReason": null, "createdAt": "…", "reviewedAt": null },
    "dealerVerified": false
  }
}
```

إذا كان الطلب مرفوضاً تعرض اللوحة السبب تحت العنوان بصيغة «سبب الرفض السابق: …» ويتحوّل الزر إلى «إعادة إرسال طلب التوثيق».

### اعتماد الإدارة: `/admin/traders-approval`

الصفحة تعرض أربعة فلاتر: «معلق» و«مقبول» و«مرفوض» و«الكل»، وزرّان لكل طلب هما «اعتماد» و«رفض».
زر الرفض يفتح نافذة فيها حقل «سبب الرفض» إلزامي، لا يقبل الإرسال فارغاً.
الضغط على «اعتماد» يستدعي `POST /api/admin/traders-approval` بالجسم `{ requestId, action: "APPROVE" }`، ويؤدي إلى:

1. تنفيذ `prisma.$transaction` واحدة تكتب `role = "TRADER"` و`dealerVerified = true` ونسخ بيانات المعرض على الحساب.
2. تغيير حالة الطلب إلى `APPROVED` مع تسجيل `reviewedBy` و`reviewedAt`.
3. كتابة حدث تدقيق باسم `TRADER_APPROVE` وإظهار تنبيه «تم اعتماد التاجر «اسم المعرض»».

الرفض يستدعي `action: "REJECT"` مع حقل `rejectReason`، ويُخزَّن السبب كما هو (أو بعبارة «لم يحدد سبب» إن غاب) في حدث `TRADER_REJECT`.

> صفحة إدارة المستخدمين `/admin/users` لا تمنح التوثيق إطلاقاً. تعليق الكود فيها صريح: «التوثيق (dealerVerified) لا يُمنح من هنا إطلاقاً — فقط عبر صفحة اعتماد التجار بعد أن يرسل التاجر طلب توثيق من لوحته».

### ما الذي يفتحه التوثيق فعلاً؟

- **الستوري:** `POST /api/stories` يرفض غير التاجر بـ `403` «الستوري متاح لحسابات التجار والمعارض فقط»، ويرفض التاجر غير الموثّق بـ `403` «حسابك قيد المراجعة — الستوري متاح بعد توثيق حسابك من الإدارة».
- **لوحة الحجوزات:** `/dashboard/bookings` تعرض لغير التاجر «هذه الصفحة مخصصة للتاجر فقط»، وللتاجر غير الموثّق «حسابك ليس موثّقًا بعد» مع وصف «طلب الاعتماد قيد المراجعة من الإدارة، وسيتم تفعيل لوحة الحجوزات فور اعتمادك».
- **نشر السيارات:** غير مرتبط بالتوثيق. `POST /api/cars` يرفض فقط بـ `403` «تم إيقاف النشر لحسابك» و`403` «حسابك محظور».

### من أين تصل إليها داخل الواجهة

- من صفحة «الملف الشخصي» `/auth/profile` زرّ أخضر باسم «لوحة التاجر والإنتاجية» يظهر لمن دوره `DEALER` أو `TRADER` أو `ADMIN` أو لمن لديه `dealerName`.
- من ملفك العام `/profile/{id}` زر باسم «لوحة التاجر» يظهر فقط عندما يكون الملف ملكك وأنت تاجر أو مدير.
- من صفحة `/dashboard/bookings` يوجد رابط مماثل في حالتك الموثّقة.
- قائمة المستخدم `UserMenuSheet` لا تحتوي هذا الرابط؛ عناصرها هي: «الملف الشخصي» و«المفضلة» و«الرسائل» و«إعلاناتي» و«مرآبي» و«طلباتي» و«تنبيهات الأسعار»، ويضاف إليها «لوحة التحكم» للمدير فقط.

> دليل المسارات المدمج في `src/ai/site-knowledge.ts` يعرّف `/workshops/dashboard` كمسار «لوحة تحكم الورشة» يتطلب مصادقة (`requiresAuth: true`)، وهو المرجع الذي يستخدمه مساعد الموقع الذكي.

## لوحة التاجر التفصيلية

اللوحة ليست صفحة بتبويبات، بل صفحة واحدة طويلة تُمرَّر بالأسفل، ويتنقل المستخدم بين أقسامها بالأزرار العلوية.
تبدأ بعرض المتجر ثم صف المشاركة ثم شارة التوثيق ثم الإعدادات ثم الستوري ثم الأرقام ثم العملاء المحتملون ثم المخزون.

### العرض العلوي وأزرار الدخول

بطاقة المتجر تعرض اسم المعرض والعنوان والوصف المختصر (سطرين كحد أقصى)، ويسبق الاسم شارة «تاجر معتمد».

> ملاحظة دقيقة من الكود: شارة «تاجر معتمد» في هذه البطاقة غير مشروطة بحالة التوثيق، فتظهر حتى لمن لم يُعتمد بعد، بينما الشارة الحقيقية للموثّق هي «موثّق» في صفحة المعرض العام.

وتحتها ثلاثة أزرار:

1. **«إضافة سيارة»** يقود إلى `/cars/new`.
2. **«معاينة المعرض العام»** يفتح `/profile/{userId}` في نفس التبويب.
3. **«تقرير الأداء»** يقود إلى `/dealer/reports`.

### صف المشاركة السريع

يعرض رابط المتجر بترتيب من اليمين إلى اليسار ثم خمسة أزرار: «نسخ الرابط» و«مشاركة واتساب» و«إعدادات المعرض» و«قالب CSV» و«استيراد CSV».
زر الاستيراد يحمل تلميحاً بالفأرة: «استيراد حتى 50 سيارة دفعة واحدة»، ويُظهر أثناء العمل نص «جاري الاستيراد...».

الاستيراد يذهب إلى `POST /api/cars/bulk-import` ويستقبل ملف CSV، وأهم حدوده:

- الحد الأقصى `MAX_ROWS = 50` صفاً في الملف الواحد.
- الحد المضاد للتكرار: «حد الاستيراد: 5 عمليات كل 10 دقائق» (`429`).
- الرد الناجح `201` يعود فيه `{ created, failed, errors }` مع أول 20 خطأ فقط.
- رسالة الحالة الفارغة: «لا توجد صفوف للاستيراد (الحد 50)».

### شارة التوثيق

تنشأ ديناميكياً حسب حالة `user.dealerVerified` وحالة آخر طلب، وقد غُطّيت بالكامل في قسم «دورة التوثيق الكاملة» في بداية الفصل.
باختصار: غير موثّق ← زر «طلب توثيق الحساب»؛ معلّق ← «طلب التوثيق قيد مراجعة الإدارة»؛ مرفوض ← عرض السبب وزر «إعادة إرسال طلب التوثيق».

### درج إعدادات المعرض

زر «إعدادات المعرض» يفتح لوحة جانبية تحوي: الشعار والصورة الشخصية وصورة الغلاف، ثم حقول «اسم المعرض» و«العنوان» و«الهاتف» و«السجل التجاري» و«الوصف».
رفع الصور يتم عبر `POST /api/upload`، وحجم الملف الواحد محدود بـ 10 ميجابايت برسالة «حجم الملف يتجاوز 10 ميجابايت».
الحفظ يتم بـ `PUT /api/auth/profile` مع الترويسة المصادقة.

### الستوري (24 ساعة)

`POST /api/stories` يتقبل `{ imageUrl, caption?, carId? }` ويضبط `expiresAt = الآن + 24 ساعة`.
الردود غير الناجحة: `400` «صورة الستوري مطلوبة»، و`403` «هذه ليست سيارتك» عند ربط إعلان لا تملكه، و`429` «تجاوزت حد النشر — حاول لاحقاً».

### ست بطاقات إحصائية

تُحسب كلها من بيانات حية لا من ثوابت:

| البطاقة | القيمة | النص التوضيحي |
|---|---|---|
| قيمة المخزون المعروض | مجموع أسعار السيارات | «متوسط … د.أ» |
| مشاهدات الإعلانات | مجموع المشاهدات | «مشاهدات الزوار» |
| مرات الحفظ بالمفضلة | مجموع الحفظات | «اهتمام المشترين» |
| استفسارات المشترين | عدد الرسائل | «رسائل على إعلاناتك» |
| إعلانات نشطة | `نشط / الإجمالي` | «سيارات متاحة الآن» |
| سيارات مباعة | `N مباعة` | «عمليات بيع ناجحة» |

تحتها قسم «أداء الإعلانات (الأعلى مشاهدة)» مع رسم بياني للمشاهدات، ثم قسم «العملاء المحتملون» المبني على `GET /api/conversations`.

### إدارة مخزون المعرض

هذا هو القسم التشغيلي الأثقل، وعنوانه الفرعي: «ابحث، رتّب، وحدّث أسعار سياراتك وحالة البيع مباشرة».

- **الفلاتر:** «الكل» ثم «المتاحة (عدد)» ثم «المباعة (عدد)».
- **البحث:** حقل بنص الإرشاد «ابحث بالماركة أو الموديل أو السنة... (مثال: كامري 2020)».
- **حالة الفراغ:** «لا توجد سيارات في معرضك حالياً» عند غياب الإعلانات، و«لا توجد نتائج مطابقة للبحث» عند عدم المطابقة.

لكل صف خمسة إجراءات:

| الإجراء | ماذا يفعل | النتيجة الظاهرة |
|---|---|---|
| تعديل السعر | `PUT /api/cars/{id}` | تحديث السعر فوراً |
| تمييز كمباعة | `POST /api/cars/{id}/sold` | «تم تمييز السيارة كمباعة!» |
| إعادة للعرض | `POST /api/cars/{id}/reactivate` | «تمت إعادة السيارة للعرض!» |
| توثيق الفحص | `PUT /api/cars/{id}` | يعرض «فحص معتمد» بدل «توثيق الفحص» |
| تمييز | `POST /api/premium-requests` | «تم إرسال طلب التمييز! ستتواصل معك الإدارة» |

زر «تمييز كمباعة» يتحول تلقائياً إلى «إعادة للعرض» عندما تكون حالة السيارة `SOLD`.
زر «تمييز» يسبقه تأكيد نصه: «طلب تمييز إعلان {الماركة} {الموديل} {السنة} ؟ ستتم مراجعة طلبك من الإدارة وتفعيل التمييز بعد تأكيد الدفع».

> لا يوجد زر حذف داخل هذه اللوحة. الحذف يتم من صفحة الإعلان نفسه `/cars/{id}` أو من `/my-cars` عبر زر «حذف الإعلان»، ويستدعي `DELETE /api/cars/{id}` وهو حذف ناعم يكتب `deletedAt` و`deletedBy` مع تسجيل `SOFT_DELETED`، ويقبل المالك أو المدير فقط.

### صفحة تقرير الأداء `/dealer/reports`

عنوانها «تقرير الأداء»، وتعرض ست بطاقات: «إعلانات نشطة» و«سيارات مباعة» و«إجمالي المشاهدات» و«قيمة المخزون» و«حفظ بالمفضلة» و«استفسارات».
تحتها جدول بالإعلانات، وزر واحد يحمل النص «طباعة / حفظ PDF» ويستخدم تنسيق طباعة مخصص لإخراج التقرير ورقياً.

## التمييز والباقات

### طلب التاجر: `POST /api/premium-requests`

الطلب بسيط ومقيّد بملكية الإعلان، ويقبل نوعين فقط:

```json
{ "carId": "clx…", "type": "FEATURE" }
```

- **المصادقة:** ترويسة JWT عادية، والدور أي مستخدم مسجّل.
- **القيد الأهم:** لا يقبل النظام أكثر من طلب `PENDING` واحد لنفس السيارة.
- **الردود:** `404` «السيارة غير موجودة»، و`400` «هذه ليست سيارتك»، و`400` «لديك طلب معلق لهذه السيارة».
- **القراءة:** `GET /api/premium-requests` يعيد طلبات المستخدم مرتبة من الأحدث.

النوعان المقبولان في الخادم هما `FEATURE` (تمييز) و`PIN` (تثبيت)، وأي نوع آخر يرد بـ «بيانات غير صالحة».

### معالجة الإدارة: `/admin/premium-requests`

الصفحة تحمل الوصف «طلبات تمييز وتثبيت الإعلانات من المستخدمين»، وفلاترها «معلق» و«مقبول» و«مرفوض» و«الكل»، وأيقونتها تسمّي النوع «تمييز» و«تثبيت».
الإجراء يستدعي `POST /api/admin/premium-requests` بجسم `{ requestId, action: "APPROVE" | "REJECT" }` وهو محصور بالمدير.

- قبول نوع `FEATURE` يضبط `featured = true` و`featuredUntil = الآن + 30 يوماً` بحساب `Date.now() + 30 * 86400000`.
- قبول نوع `PIN` يحدّث حالة الطلب إلى `APPROVED` فقط، فلا يوجد حقل «مثبّت» في نموذج السيارة داخل `prisma/schema.prisma`.
- الرفض يكتب `REJECTED` دون تعديل الإعلان، والردود هما «تم قبول الطلب» و«تم رفض الطلب».
- إن كان الطلب قد عولج سابقاً يرد المسار بـ «تم معالجة الطلب مسبقاً».

### التمييز المباشر من الإدارة: `/api/admin/cars/{id}/feature`

| الطريقة | المسار | المصادقة | الأثر |
|---|---|---|---|
| POST | `/api/admin/cars/{id}/feature` | `ADMIN` فقط | تمييز حسب مدة الباقة |
| DELETE | `/api/admin/cars/{id}/feature` | `ADMIN` فقط | إلغاء التمييز |

جسم الطلب هو `{ planId }`، والمدة تُقرأ من الباقة المختارة عبر `plan.durationDays`، ونموذج الباقة في نموذج الإدخال يبدأ بـ 30 يوماً.
عند التفعيل يُنشأ إشعار داخل التطبيق بعنوان «إعلان مميز» ويُرسَل إشعار واتساب للمالك بقالب `car_featured`.
في الواجهة يظهر التنبيه «تم تمييز الإعلان»، وعند الإلغاء «تم إلغاء التمييز» مع تصفير `featured` و`featuredUntil`.

### الباقة والاشتراك في قاعدة البيانات

نموذجان منفصلان، لا تخلط بينهما:

- **`Plan`**: يديرها `/admin/plans` ويحوي `nameAr` و`nameEn` و`price` و`durationDays` و`features` و`isActive`، وهي المستخدمة في تمييز الإعلانات.
- **`Subscription`**: يديرها `/admin/subscriptions` ويحوي `plan` (افتراضي `BASIC`) و`status` (افتراضي `ACTIVE`) و`price` و`startDate` و`endDate` و`autoRenew` افتراضياً `true`.

اخترارات صفحة الاشتراكات تسمّي الباقات: «الأساسية» و«الفضية» و«الذهبية» و«البلاتينية»، وتخزن في الحقل كقيم `BASIC` و`SILVER` و`GOLD` و`PLATINUM`.
إجراءات الإدارة عليها: تأكيد بـ «هل أنت متأكد من تفعيل اشتراك هذا المستخدم؟» أو «… تعطيل …»، وتمديد عبر حقل نصي مكتوب فيه مثاله «تمديد الاشتراك بعدد أيام (مثال: 30):» بقيمة افتراضية 30، وحذف نهائي بتأكيد.

> الأسعار ومدد الباقات قابلة للتعديل من `/admin/plans` وتُخزَّن في قاعدة البيانات، لذا لا توجد «سعر ثابت» يمكن ذكره في الدليل كقيمة دائمة.

## صفحة المعرض العامة

الصفحة هي `/profile/{userId}`، وهي الوجه الذي يراه المشتري لمعرضك، وليست لوحة تحكم.

### شروط الظهور كمعرض

الصفحة تحتسب `isDealer` عندما يوجد `dealerName` أو يكون الدور `TRADER` أو `DEALER`، وتحسب `isVerifiedTrader` من `dealerVerified`.
الشارة الظاهرة هي «موثّق» بعنوان تلميحي «تاجر موثّق»، ويوجد بجانبها شارة أخرى للهاتف بعنوان «رقم هاتف موثّق».

### مكونات الصفحة من الأعلى للأسفل

- **البانر والشعار** مع اسم المعرض.
- **أزرار التفاعل:** «متابعة» بعدد «N متابِع» و«N يتابع»، ثم تواصل واتصال ومشاركة.
- **زر داخلي:** «لوحة التاجر» يظهر فقط لمالك الملف حين يكون `TRADER` أو `DEALER` أو `ADMIN`.
- **النبذة:** «نبذة عني» للحسابات الفردية و«عن المتجر» لحسابات المعارض.
- **التقييم** مع عدّاد التقييمات.
- **دقة الأسعار** وهي أداة فريدة في هذا الموقع.
- **العدّادات:** عدد الإعلانات والمنشورات، ثم بطاقة «مشاهدة الملف» بعدد مشاهدات الملف الكلي.
- **«آخر التقييمات»** وقسم **«إعلانات {اسم المعرض}»** بشكل شبكة.

### دقة الأسعار: كيف تُحسب

المصدر هو `GET /api/users/{id}/accuracy` وهو مسار عام لا يحتاج مصادقة.
الدرجة تبدأ من 100 وتُخصم منها ثلاث نقاط عن كل نسبة مئوية واحدة من ارتفاع السعر فوق متوسط السوق، والصيغة: `100 - 3 × (متوسط نسبة التضخم بال٪)`.

| النتيجة | التسمية المعروضة |
|---|---|
| 85 فأعلى | أسعار عادلة جداً |
| من 65 إلى 84 | أسعار معقولة |
| من 40 إلى 64 | أسعار مرتفعة غالباً |
| أقل من 40 | مبالغ بأسعاره غالباً |
| لا بيانات كافية | لا توجد بيانات كافية |

تظهر في الصفحة كسطر: «دقة الأسعار: أسعار معقولة» مع الدرجة على طراز `87/100`، ومعها عبارة «بناءً على N إعلان بتقييم AI».

> البيانات لا تُحسب من إدخال يدوي. الخادم يقرأ إعلاناتك ويقارن أسعارها بالسوق عبر تقييم ذكاء اصطناعي، لذا فإن رفع سعر إعلان واحد مرتفعاً يخفض الدرجة مباشرة.

## لوحة صاحب الورشة /workshops/dashboard

اللوحة صفحة واحدة بتبويبات عشرة، وكلها تُحمَّل بطلبات متوازية في نفس التحميل الأول.

### شروط الدخول

الخادم يبحث عن ورشة يملكها المستخدم نفسه: `prisma.workshop.findFirst({ where: { userId: user.id } })`.
إن لم يجد ورشة ردّ `404` برسالة «الورشة»، أي أن أي مستخدم بلا ورشة لا يرى بيانات مهما صلاحياته.

```ts
export async function GET(request: NextRequest) {
  const user = await authenticateRequest(request);
  if (!user) return unauthorizedResponse();
  const workshop = await prisma.workshop.findFirst({ where: { userId: user.id } });
  if (!workshop) return notFoundResponse('الورشة');
  return successResponse(workshop);
}
```

حقل `PUT` في المسار نفسه يقبل: `name` و`description` و`phone` و`whatsapp` و`email` و`website` و`address` و`lat` و`lng` و`cityId` و`provinceId` و`logo` و`coverImage` و`workingHours` و`workingDays` و`yearsOfExperience` و`employeeCount`.

### التبويبات العشرة

تظهر بالترتيب: «نظرة عامة» و«تعديل الورشة» و«الخدمات» و«الماركات» و«الأسعار» و«المواعيد» و«التقييمات» و«إنشاء إعلان» و«إعلاناتي» و«الإحصائيات».

### نظرة عامة: سبع بطاقات

«المشاهدات» و«الرسائل» و«المواعيد» و«المكالمات» و«السيارات المصليحة» و«التقييم» و«عدد التقييمات»، وجميعها تأتي من `GET /api/workshops/dashboard/stats` لا من قيم ثابتة.

### إدارة المواعيد

حالات الموعد تظهر بهذه الأسماء حرفياً: «قيد الانتظار» و«مؤكد» و«مكتمل» و«ملغي» و«مقبول» و«مرفوض» و«منتهي».
للموعد الذي حالته `PENDING` أو `CONFIRMED` تتوفر خمسة إجراءات:

1. **تأكيد** ← تغيير الحالة إلى `CONFIRMED`.
2. **تعيين السعر النهائي** ← نافذة تكتب `finalPrice` وتثبّت الحالة `CONFIRMED`.
3. **إكمال** ← تغيير الحالة إلى `COMPLETED`.
4. **رفض مع سبب** ← نافذة سبب إلزامية بحد أقصى 500 حرف، والحالة `REJECTED`.
5. **إلغاء** ← تغيير الحالة إلى `CANCELLED`.

كل تعديل يمر بـ `PUT /api/workshops/dashboard/appointments` مع ترويسة المصادقة.

### التقييمات والإعلانات

ردّ الورشة على التقييم يتم بـ `PUT /api/workshops/dashboard/reviews` بالجسم `{ reviewId, workshopReply }`، ولا يقبل الرد إن كان هناك رد موجود مسبقاً.
إعلانات الورشة تُنشَأ بجسم `FormData` إلى `POST /api/workshops/dashboard/ads`، ويُحذف بـ `DELETE /api/workshops/dashboard/ads/{id}` الذي يرد «تم حذف الإعلان بنجاح».
الخدمات والماركات والأسعار لها مسارات مطابقة مع مسارات حذف فرعية مثل `/api/workshops/dashboard/services/{id}`.

### تبويب «الإحصائيات» — بيانات تجريبية ثابتة

> تنبيه مهم ومُتحقَّق منه في الكود: تبويب «الإحصائيات» في `src/app/workshops/dashboard/page.tsx` يعرض **أرقاماً ورسماً بيانيين مكتوبين يدوياً** وليس بيانات حية.
> قيم النمو التالية ثابتة في المصدر ولا تتغير مهما تغيّرت أرقامك: `+12%` للمشاهدات و`+5%` للرسائل و`+8%` للمواعيد و`+3%` للمكالمات و`+15%` للسيارات المصليحة.
> كذلك الرسم البياني في قسم «ملخص النشاط» يحمل تسمية إنجليزية واحدة `Views trend` ومصفوفة ثابتة من 12 قيمة: `30, 45, 60, 55, 80, 70, 90, 85, 95, 100, 110, 120`، وأعمدته تُقاس بالنسبة إلى 120.
> القيم الرقمية داخل البطاقات نفسها (المشاهدات والرسائل…) تأتي من `stats` الحقيقية، لكن نسبة التغير والمنحنى حولها تجريبية.

## مسارات الورش الأخرى

### الفهرس العام `/workshops`

صفحة تسويقية وفهرس بحث معاً، وحقل البحث فيها يحمل النص «ابحث باسم الورشة، المدينة، أو تخصص الفحص...» وزر «بحث»، مع زر فرعي «تصفية نتائج البحث المتقدمة».
حالة عدم وجود نتائج تظهر بعنوان «لم نجد ورشات تطابق البحث».
الصفحة تعرض أيضاً أسعاراً تقريبية كمرجع، مثل خدمة «تغيير زيت وفلتر أصلي» بحدود 25–55 د.أ مع ملاحظة «يعتمد على نوع الزيت وسعة المحرك».

### صفحة الورشة `/workshops/{id}`

- عنوان الورشة بخط عريض، وحالة عدم الوجود تظهر بـ «الورشة غير موجودة».
- ثلاثة أزرار رئيسية: «حجز موعد فوري» و«اتصال» و«واتساب».
- جدول الخدمات بأعمدة «اسم الخدمة» و«حجز» مع زر «حجز الخدمة» لكل صف.
- بلوك «احصل على العرض عند الحجز» وزر محادثة «محادثة واتساب».
- بلوك «حجز موعد مسبق» يشرح: «حدد التاريخ والوقت المناسب لك واطلب خدمة الفحص أو الإصلاح مباشرة» وزر «احجز موعدك الآن».

النافذة المنبثقة تحمل العنوان «حجز موعد لدى اسم الورشة» وحقلين إلزاميين هما «تاريخ الموعد *» و«نوع الخدمة *» مع اختيار الوقت.
عند النجاح يظهر: «تم إرسال طلب الحجز بنجاح!» مع «سيتواصل معك فريق الورشة لتأكيد موعدك».
وعند نقص البيانات يظهر: «حدث خطأ، يرجى اختيار التاريخ والوقت والخدمة»، وزر الإرسال هو «تأكيد الحجز والإرسال».

### تسجيل ورشة جديدة `/workshops/create`

التسجيل علني لأي مستخدم مسجّل، وغير المسجّل يُحوَّل إلى `/auth/login?redirect=/workshops/create`.
النموذج أربع خطوات: «المعلومات الأساسية» ثم «الخدمات والماركات» ثم «الأسعار التقريبية (اختياري)» ثم «مراجعة وإرسال».
رسائل التحقق: «اسم الورشة مطلوب» و«أدخل رقم الهاتف أو الواتساب» و«اختر خدمة واحدة على الأقل».

الإرسال يتم بـ `POST /api/workshops`، وهذه قيمه الافتراضية حين لا يُمرَّر الحقل:

```text
workingHours = "08:00-17:00"
workingDays  = "Sun-Thu"
priceRange   = "moderate"
isVerified   = false
isBanned     = false
isPaused     = false
```

> الاستعلام العام للورش يستبعد الحقول الحساسة `isBanned` و`isPaused`، فلن تظهر ورشة محظورة أو موقوفة في الفهرس حتى لو عُرف رابطها.

### وجهة الإدارة: `/admin/workshops/review`

أربعة تبويبات: «ورش بانتظار المراجعة» و«كل الورش» و«إعلانات الورش» و«البلاغات»، وفلاتر حالة: «الكل» و«موثقة» و«محظورة» و«موقفة».
مدد الحظر في هذه الصفحة خمس: «يوم واحد» و«3 أيام» و«أسبوع» و«شهر» و«دائم».
التوثيق يتم بـ `PUT /api/admin/workshops` بالجسم `{ workshopId, isVerified: true }`، والرفض يضبط `isBanned = true` مع السبب، والحظر يحسب تاريخ انتهائه `banUntil`.
صفحتا `/admin/workshops` و`/admin/workshops/ads` تستخدمان مدد حظر مختلفة: «حظر دائم» و«7 أيام» و«30 يوم» و«90 يوم» و«سنة»، مع نافذة إيقاف منفصلة تحوي «سبب الإيقاف» وحقل «إلى تاريخ» يكتب `pauseReason` و`pausedUntil`.

## صلاحيات التاجر مقابل المدير مقابل المستخدم

جدول واحد يلخّص الفروق العملية التي تراها يومياً:

| القدرة | التاجر (TRADER/DEALER) | المدير (ADMIN) | المستخدم (USER) |
|---|---|---|---|
| تصفح الإعلانات والورش | نعم | نعم | نعم |
| نشر إعلان سيارة | نعم ما لم يكن موقوفاً | نعم | نعم ما لم يكن موقوفاً |
| طلب توثيق تاجر | نعم | نعم | لا — «طلب التوثيق متاح لحسابات التجار فقط» |
| اعتماد التوثيق | لا | نعم من `/admin/traders-approval` | لا |
| نشر ستوري 24 ساعة | نعم بعد التوثيق | نعم | لا |
| طلب تمييز إعلان | نعم لإعلاناته فقط | نعم لإعلاناته فقط — «هذه ليست سيارتك» | نعم لإعلاناته |
| منح التمييز فعلياً | لا | نعم من `/admin/premium-requests` و`/admin/cars` | لا |
| حذف إعلان | ملكه فقط | أي إعلان | ملكه فقط |
| إدارة ورشة | ورشته هو فقط | كل الورش | بلا ورشة = `404` |

### الفرق بين التاجر والمدير في طبقة الخادم

الخادم لا يثق بفحوص الواجهة، ويُعيد فرض هذا الفرق نفسه عند كل نقطة نهاية:

```ts
// مسار يتطلب تاجراً أو مديراً — src/app/api/trader/verification/route.ts
if (user.role !== 'TRADER' && user.role !== 'DEALER' && user.role !== 'ADMIN') {
  return errorResponse('طلب التوثيق متاح لحسابات التجار فقط', 403);
}

// مسار يتطلب مديراً فقط — src/app/api/admin/premium-requests/route.ts
if (!user || user.role !== 'ADMIN') return unauthorizedResponse();
```

> القاعدة العملية: التاجر يدير مملكته (إعلاناته ومخزونه وملفه وطلبات توثيقه وتمييزه)، والمدير يدير القاعدة (يعتمد ويرفض، يمنح التمييز، يعدّل الأدوار والاشتراكات)، والمستخدم يتصفح ويتفاعل.
> حتى لو فُتح مسار إداري بروابط مباشرة، يبقى الرد `401` أو `403` لأن كل مسار يستدعي `authenticateRequest` ثم يفحص الدور.

### الصلاحيات المرتبطة بحالة التوثيق لا بالدور

ثلاثة أمور لا تُحسم بالدور بل بقيمة `dealerVerified`: نشر الستوري، ورؤية لوحة الحجوزات، وظهورك في دليل «الوكلاء والمعارض» الذي يستعلم عن `role = "DEALER"` مع `isActive = true` و`dealerVerified = true`.
لذلك قد تكون تاجراً بالدور وبلا إعلانات موثقة في الدليل العام حتى تُعتمد من الإدارة.
